# ADR-0011：跨数据库与对象存储采用停写一致恢复点

- 状态：已接受
- 日期：2026-07-29

## 背景

系统事实同时存在 PostgreSQL 和 MinIO。两者没有分布式事务或共同快照：数据库记录可能引用
对象键，而对象写入与数据库提交之间使用补偿删除。分别在线备份可能得到时间点不一致的两份
副本，恢复后出现缺失对象或孤儿对象。

## 决策

本地备份基线采用短暂停写的一致恢复点：

1. 停止后端，保留 PostgreSQL、MinIO 和 ClamAV 运行。
2. 对 PostgreSQL 执行 custom-format `pg_dump`，不保存所有者和权限。
3. 使用官方 MinIO Client 将应用桶镜像到同一恢复点目录。
4. 保存逐表精确行数、对象数量和字节数。
5. 对数据库归档、元数据和全部对象生成 SHA-256 manifest。
6. 使用 `pg_restore --list` 和 manifest 做无写入完整性校验。
7. 重新启动后端并执行健康与冒烟检查。

脚本在检测到 8080 后端仍监听时默认拒绝备份；`-AllowOnline` 只用于调用者明确接受跨存储
不一致风险的场景，不能作为正式恢复点默认方式。

恢复只允许写入带安全前缀且尚不存在的新数据库和新桶，不提供覆盖当前
`medical_agent`/`medical-agent-files` 的快捷开关。pgvector 由管理员在新库预装，恢复清单
跳过扩展创建和扩展注释，业务对象由最小权限应用角色恢复。

恢复后必须逐表比对行数、比对对象数量/字节数，并将恢复桶重新下载后逐对象比对 SHA-256。
正式切换应通过新目标验证、配置切换和可回滚变更完成，不能在原目标上直接重放。

## 后果

- 本地可以证明备份可读、可恢复，而不是只证明命令执行成功。
- 停写窗口随数据量增长；当前脚本未建立生产 RPO/RTO 承诺。
- 恢复目录可能包含敏感业务数据，已从 Git 排除，但仍需加密磁盘、最小文件权限、异地副本、
  保留策略和访问审计后才能用于生产。
- 自动过期删除没有纳入脚本，避免在保留策略未审批前误删唯一恢复点。

## 验证

2026-07-29 在本机完成两次随机临时恢复演练。最终演练对 45 张 public 表逐表比对行数；
MinIO 使用一个明确标记 `SYNTHETIC_ANONYMOUS` 的对象验证镜像、恢复下载和 SHA-256 一致。
临时数据库和源/目标桶全部清理，应用重新启动后五项服务为 `UP`，8 项冒烟通过。
