## 2. 完成范围

### 2.1 公开课题标识与身份规范化

- V24 为所有课题回填 `prj_` 加 26 位大写 Crockford Base32 的全局唯一公开 key。
- Java 创建路径使用 `SecureRandom`；数据库回填使用内置随机 UUID，不依赖可选扩展。
- 格式检查、唯一约束和更新触发器共同保证 key 合法且不可变。
- 医院编码执行 NFKC、去空白、大写和 ASCII 白名单规范化。
- 用户名执行 NFKC、去空白及小写规范列；医院账号和平台账号分别建立唯一边界。
- 公开课题查询使用登录医院和 `projectKey`，返回视图不包含课题内部 UUID。
- 非法、未知、跨医院和非成员探测采用相同 `PROJECT_NOT_FOUND` 404 边界。

### 2.2 数据库级医院隔离

- V25 为所有同时包含 `hospital_id` 和 `id` 的父表建立组合唯一索引。
- 依据真实 PostgreSQL 目录为所有适用父子关系补充 `(hospital_id, foreign_id)` 组合外键。
- 组合外键先 `NOT VALID` 创建，再显式验证；发现历史错挂时整体失败关闭。
- 原外键的级联/限制语义保持不变，不自动删除、合并或重挂数据。
- 身份管理、成员解析、任务、审核和导出等查询均在仓储入口携带医院条件。

### 2.3 三方审核和语义失效

- V26 增加审核轮次、规范化内容哈希、统计审核字段和追加式决定历史。
- 医学审核、统计审核和负责人确认默认由三个不同账号完成。
- 医学或统计任一退回即阻断负责人确认；退回前必须有本轮、本人、对应职责的定位批注。
- 两类专家均通过且内容哈希一致后，负责人才能确认并锁定章节。
- 被审核内容发生语义变化时创建新轮次并清空当前决定，旧历史仍可追溯。
- 旧 V17 审核统一标记为 `SUPERSEDED/legacy_review`，不会被解释为三方通过。
- 导出再次校验课题负责人、三方状态、锁定状态、方案 ID、内容哈希和已核验引用。

### 2.4 兼容边界

- `/workspace/legacy` 和旧工作台的 UUID 命令接口继续作为 compatibility-only 能力存在。
- 公开课题详情使用 `projectKey`；UUID 详情入口已迁入 `/legacy/{id}`。
- 第二阶段 V2 页面不得调用任何 legacy UUID 入口；每个纵向切片通过门禁后再按环境开启。

## 5. 发布、迁移与回退

固定发布顺序：

1. 维护窗口停止旧后端和 Worker，阻止新任务；
2. 确认没有 `RUNNING` Agent 任务；
3. 完成数据库、对象存储清单备份和只读重复/跨院扫描；
4. 执行 V20～V26；
5. 核对 Flyway 历史、`project_key` 回填、规范化唯一性、组合外键和旧审核失效结果；
6. 只启动新版本后端，再启动前端；
7. 执行登录、课题、成员、文件、Agent、三方审核和导出冒烟。

如果迁移前扫描发现规范化重复、跨院错挂或仍在运行的 Agent 任务，必须停留在 V19 并人工处置；
不得自动清理数据。数据库迁移为前向迁移，回退方式是恢复维护窗口前备份并恢复旧应用，禁止在
V20～V26 结构上混跑旧代码。

## 6. 剩余非阻断事项

- 旧工作台仍依赖 compatibility-only UUID API；由第二、三阶段逐纵向切片替换。

- PostgreSQL 18.4 高于当前 Flyway 明确测试上限，迁移已实测通过，但升级 Flyway 版本列为 P2。
- 外部 DeepSeek、MinIO 和第三方联机测试需要独立环境或凭据，未伪造通过。

以上事项不影响 P0-B `PASS`，并已转入后续阶段追踪。
