# P0-B 实施与 Review 计划

- 日期：2026-07-30
- 当前状态：`PASS`
- 前置阶段：P0-A `PASS`
- 执行策略：全部采用 V1.2 推荐默认值
- 运行库边界：当前本地运行库仍为 V19，本阶段未在旧应用运行期间执行 V20～V26

## 1. 阶段目标

P0-B 将应用层的医院隔离提升为“公开标识、SQL 查询、数据库约束和授权测试”共同保证，并把
现有单一通用专家审核改造成 ADR-0012 冻结的医学审核、统计审核和课题负责人确认三方门槛。

退出时必须同时满足：

1. 浏览器侧使用不可枚举且不可变的 `projectKey`，普通 V2 响应不返回内部 UUID；
2. 所有具有医院归属的父子关系由 `(hospital_id, id)` 组合键约束；
3. 面向登录用户的业务查询在 SQL/仓储入口携带 `hospital_id`，不采用查全库后过滤；
4. 不存在、非法格式、跨医院和非成员课题探测采用一致 404 边界并留下安全审计；
5. 文件、对象存储和导出下载重新验证医院、课题成员及业务状态；
6. 医学审核、统计审核和负责人确认由三个独立账号完成，任何语义修订使旧审核失效；
7. 后端、前端、空库迁移、V19 升级、真实 PostgreSQL 和跨医院负向门禁全部通过；
8. 独立 Review 后无遗留 P0/P1。

## 2. 现状核验结论

### 2.1 公开课题标识

- 原 `research_project` 只有内部 UUID 和院内 `project_code`，没有公开标识；
- 当前兼容 API、前端和 Agent 工作台仍普遍使用 UUID；
- 阶段 0 已冻结格式：`prj_` + 26 位大写 Crockford Base32，密码学安全随机、全局唯一、
  创建后不可变；
- 非法 key 与不存在/跨医院 key 必须统一为 `404 课题不存在`。

### 2.2 身份规范化

- 登录查询原先使用 `lower(...)`，数据库唯一约束却区分大小写；
- `(hospital_id, username)` 对 `hospital_id IS NULL` 的平台账号不能形成期望的唯一边界；
- 创建医院和用户只做 `trim`，没有 Unicode NFKC 规范化；
- `HospitalService.listUsers` 原先查全库后在 Java 中过滤，`disableUser` 先按全局用户 ID 查询；
- 阶段 0 只读扫描未发现现存大小写/空白重复，因此可以失败关闭地增加约束，不需自动清理。

### 2.3 医院关系

- V19 有 45 张业务表，V20～V23 新增 3 张，共 48 张；
- 阶段 0 动态检查的 80 组既有医院关系当前跨院异常为 0；
- 大多数父子关系仍只有单列 UUID 外键，错误的
  `hospital_id=A, project_id=医院B课题` 可绕过数据库；
- 除定时保留清理、Worker 全局领取、会话 token 查找等非“登录用户资源查询”外，主要业务仓储
  已接收 `hospitalId`；身份管理的查全库后过滤缺口需要修复。

### 2.4 授权和审核

- 课题非成员访问通常已使用 404；合法成员但无写权限使用 403，边界合理；
- 文件上传在写对象前调用 `requireEditable`，导出下载按登录医院读取导出记录后再次校验课题成员；
- 仍缺少“伪造 projectKey、跨医院文件、跨医院导出”的统一自动化矩阵；
- 当前审核模型只有一个 `EXPERT` 决策加负责人确认，不满足医学、统计、负责人三个独立账号要求；
- 现有历史审核不得自动解释为新审核矩阵下的三方通过。

## 3. 分切片实施

### B1：公开标识与身份规范化

状态：`PASS`

实施内容：

- V24 为存量课题安全回填 `project_key`；
- 随机源使用两个 PostgreSQL 内置安全随机 UUID，生成 26 位 Crockford Base32，提供 130 bit
  随机空间，不依赖可选 `pgcrypto`；
- 全局唯一、格式检查和更新触发器共同保证不可变；
- Java 创建路径使用 `SecureRandom`，内存/PostgreSQL 仓储保持一致；
- 新增按登录医院和 `projectKey` 查询的公共视图，不返回课题内部 UUID；
- 医院编码执行 NFKC、去首尾空白、转大写及 ASCII 白名单；
- 用户名执行 NFKC、去首尾空白，数据库生成小写规范列，并分别约束医院账号和平台账号；
- 医院管理员用户列表/禁用、课题成员解析和导出负责人解析改为医院范围查询。

Review/测试：

- 10,000 个随机 key 格式和重复回归；
- 非法/未知/跨医院 key 一致 404；
- 全角用户名、大小写和空白规范化；
- 随机空库 V1～V24；
- 带存量课题的 V19→V24；
- key 更新和同院规范化重复写入拒绝。

### B2：数据库组合键与租户 SQL

状态：`PASS`

实施内容：

- V25 为所有同时具有 `hospital_id` 和 `id` 的父表建立 `(hospital_id, id)` 唯一索引；
- 基于迁移时实际 PostgreSQL 目录，为所有“子表和父表均有医院归属”的单列 ID 外键补充组合外键；
- 每条组合外键先以 `NOT VALID` 建立，再在同一迁移中显式验证；发现现存错挂即使整个迁移回滚，
  不删除、不改挂、不合并数据；
- 保留原外键的级联语义，新增约束只强化医院一致性；
- 面向登录用户的身份管理查询补齐 SQL 医院条件。

Review/测试：

- 自动证明所有符合条件的原单列外键都有对应组合外键；
- 两医院允许同用户名、同课题编码和同课题名；
- 跨院课题成员、文件、Agent 任务及子资源写入由 PostgreSQL 拒绝；
- 随机空库 V1～V25 和 V19→V25；
- 迁移测试数据库全部自动删除。

### B3：API、防枚举、文件与导出授权

状态：`PASS`

实施内容：

- 为 V2 建立只接受 `projectKey` 的课题解析边界；公开课题视图不返回内部 UUID；
- 课题 UUID 详情入口迁入 `/legacy/{id}`；旧工作台尚未迁移的 UUID 命令接口继续按
  compatibility-only 管理，阶段 2 的 V2 页面不得调用；
- 统一不存在、非法 key、跨医院和非成员为同一 404 响应；
- 对失败的 key 探测记录脱敏安全审计，不把“医院存在/课题存在但无权限”差异反馈给客户端；
- 复核会话、强制改密、RBAC、上传、下载、对象键和 Content-Disposition；
- 两医院伪造 key、跨院课题/任务/文件写入以及导出下载都重新验证医院和课题访问权。

### B4：医学、统计与负责人审核矩阵

状态：`PASS`

实施内容：

- V26 新建审核轮次、审核职责、不可变决定历史和规范化内容哈希；
- 医学、统计、负责人分别建模，默认要求三个不同账号；
- 医学/统计审核人必须是本院课题成员、具备专家角色，并在当前轮次绑定唯一职责；
- 任一退回阻断负责人确认；语义内容变化将当前轮次三类结论标记为 `SUPERSEDED`；
- 两类专家通过且内容哈希一致后，负责人方可确认和锁定；
- 科研草案导出重新校验三方状态、内容哈希和免责声明；
- 旧 V17 审核只保留历史，不自动回填为新三方通过。

## 4. 迁移与发布边界

当前运行库仍为 V19，旧应用不认识 V20～V26。实际发布必须沿用 P0-A 冻结顺序：

1. 维护窗口停止旧后端/Worker并阻止新任务；
2. 确认无 `RUNNING` 任务；
3. 在只读可重复读事务中重跑规范化、重复和跨医院扫描；
4. 备份数据库和对象存储清单；
5. 执行 V20～当前最新迁移；
6. 核对 `projectKey` 回填、组合外键、表计数和 Flyway 历史；
7. 只启动新版本应用；
8. 执行登录、课题、成员、文件、Agent、审核和导出冒烟。

如果扫描发现重复或跨医院错挂，本阶段只输出清理清单并暂停迁移；未经项目负责人逐项确认，不会
自动删除、合并、改名或重挂任何数据。
