# 第四阶段实施与 Review 计划：多模型、受控生成、评测与成本治理

- 日期：2026-07-30
- 当前状态：`DOING / 现状核验完成`
- 前置阶段：第三阶段 `PASS`
- 执行策略：全部采用 V1.2 推荐默认值
- 外部调用边界：默认关闭；本阶段自动化只使用确定性 Mock/WireMock，不调用真实供应商
- 运行库边界：当前 V19 运行实例保持不变；V28 及后续迁移只允许在随机临时数据库验证

## 1. 目标

第四阶段在不削弱现有确定性规则、人工审核和科研草案边界的前提下，引入可配置的多模型路由、
章节级模型候选、独立复核模型、内容—依据一致性门禁、可追溯评测、专家评分和课题成本审计。

退出时必须达到：

1. 业务按逻辑模型类型路由，不直接依赖 DeepSeek 或具体模型名；
2. 真实多模型配置可为 FAST、STANDARD、REASONING、REVIEW 指定不同 Provider/模型；
3. 生成模型和复核模型必须是不同模型身份；不允许静默退回同一模型自审；
4. 模型每次只生成一个章节候选，候选不会自动覆盖当前方案，必须通过确定性校验和医生明确采纳；
5. 模型只能引用本次分配的公开证据标识；未核验 PMID、DOI、NCT 或引用 key 必须失败关闭；
6. 模型复核只产生建议和问题，不产生医学、统计、伦理或负责人批准；
7. 三类观察性研究规则继续是硬边界，模型只能在规则允许范围内提供解释性建议；
8. 匿名合成评测运行、自动指标和医学/统计专家评分可持久化、追溯和导出报告；
9. 每次调用记录逻辑类型、路由版本、Provider 用量、计价版本和估算成本；按课题聚合；
10. 外部调用默认关闭，价格未知、预算不足、复核路由相同或输出不合规时失败关闭；
11. 后端、真实 PostgreSQL、契约、前端、E2E、安全、质量和成本门禁通过；
12. Review 后无遗留 P0/P1。

## 2. 现状核验与代码证据

### 2.1 已有基础

- `ModelRouter` 和 FAST、STANDARD、REASONING、REVIEW 四种逻辑类型已经存在；
- DeepSeek 使用 OpenAI 兼容 `/chat/completions`、JSON 输出、外部调用显式开关和输入安全门；
- V20 `ai_model_call_log` 已保存医院、课题、任务、步骤、Provider、模型、Prompt、Schema、哈希、
  状态和保留期限；
- STEP13 使用版本化确定性模板生成 18 章，STEP15 只链接 STEP10 已核验的 PubMed 元数据；
- 已有 5 个 `SYNTHETIC_ANONYMOUS` 合成案例和结构化自动评测；
- 三方人工审核、章节版本、工作区 V2 和科研草案导出门禁已在第三阶段通过。

### 2.2 真实差距

- DeepSeek/Mock 两个路由实现都忽略逻辑类型，将四种类型返回同一实例；
- `ResearchModel` 只支持研究想法分析，不能生成单章候选或执行独立复核；
- DeepSeek 响应没有提取 Provider request ID、prompt/completion/total Token 和缓存 Token；
- 模型审计快照把逻辑类型硬编码为 FAST，没有路由策略、用量、计价或成本字段；
- 没有课题预算和调用前成本门禁，价格未知时也无法失败关闭；
- 方案生成仍是整份确定性模板，没有模型候选、允许引用集、校验结果和人工采纳记录；
- 现有主张—引用校验能避免模板伪造 PMID/DOI，但尚未覆盖模型章节候选中的标识符；
- 设计推荐只有规则评分，没有受规则约束的模型解释或独立复核；
- 合成评测只在测试进程中返回内存结果，没有持久化运行、盲评材料、专家评分或阶段报告；
- 没有面向课题负责人的模型用量与成本读模型。

## 3. 冻结的推荐默认值

### 3.1 路由和失败策略

- 默认 `mock` 模式继续零外部调用，但为四种逻辑类型提供不同的稳定模型身份；
- 新增 `multi` 模式，使用 OpenAI-compatible Provider 配置，可为每种逻辑类型设置独立
  `provider/model/baseUrl/credentialRef`；
- 生成章节默认走 `RESEARCH_STANDARD`，复杂方法学建议可显式走 `RESEARCH_REASONING`，
  复核固定走 `RESEARCH_REVIEW`；
- `RESEARCH_REVIEW` 与实际生成路由的 `provider + model` 不得相同；启动和调用前双重校验；
- 不做跨 Provider 静默回退；失败保留可审计记录，由用户使用新幂等键明确重试；
- 路由策略版本固定写入每次调用；页面只显示中文用途和已脱敏的 Provider/模型信息。

### 3.2 Token、价格和预算

- Provider 返回用量时记为 `PROVIDER_REPORTED`；没有用量时为 `NOT_AVAILABLE`，不得伪造精确 Token；
- 价格按配置的版本化“每百万输入/缓存输入/输出 Token 微币值”计算，使用整数避免浮点误差；
- 币种显式保存 ISO 4217 代码；价格缺失时成本状态为 `UNPRICED`，不得显示为 0；
- 真实外部生成/复核要求价格已配置，否则失败关闭；
- 默认单次输出上限 4096 Token、单次估算成本上限 0.25 USD、单课题累计上限 5 USD；
- 预算检查在调用前和调用后各执行一次；超限不继续调用，也不自动切换模型；
- Mock 用量只标记为测试数据，不计入真实供应商成本。

### 3.3 章节候选与依据门禁

- 模型一次只接收一个章节的结构、已确认事实、允许证据 key 和必要摘要片段；
- 不把其他任务原始输出、内部 UUID、对象 key 或真实患者信息发送给模型；
- 输出 Schema 只含章节 code、Markdown 内容、使用的证据 key、待确认项和自述限制；
- Java 校验章节 code、长度、格式、禁止表述、三类研究范围和引用 allowlist；
- 扫描所有 PMID、DOI、NCT 和引用 key；任何未分配标识符都拒绝整个候选；
- 候选先独立持久化，不改变当前章节版本；只有 OWNER/EDITOR 明确采纳后才追加新版本；
- 采纳后清除下游派生快照并进入既有安全重提交/新审核轮次流程；
- 空变化不得制造新版本，锁定章节不得生成或采纳候选。

### 3.4 复核和研究类型边界

- 复核模型只返回结构、引用、方法学和安全问题及严重度，不返回 `APPROVED`；
- 复核结果标记为“模型辅助复核建议”，不能满足任何一项人工审核门槛；
- 研究类型硬限制仍由版本化规则执行；模型不得新增第四种类型，不得覆盖规则缺失项；
- 模型建议与规则冲突时显示冲突并阻断采纳，规则结论优先。

### 3.5 评测与专家评分

- 继续只使用合成匿名案例；真实匿名历史课题未获批前不进入自动化；
- 自动评测覆盖 Schema、三类研究范围、必需澄清、禁止编造、章节引用 allowlist、复核独立性和成本；
- 每次评测保存数据集、Prompt、路由、模型、输出哈希、自动指标和失败原因，不保存不必要原文；
- 医学和统计专家分别按 1～5 分评价正确性、完整性、安全边界和可执行性，并可给出退回意见；
- 两类专家评分必须来自不同 EXPERT 账号；评测报告明确“技术评测/内部评分，不是伦理或正式批准”；
- 缺少真实专家输入时状态保持 `WAITING_EXPERT_SCORING`，不伪标通过。

## 4. 公开契约

### 4.1 只读端点

- `GET /api/research/projects/{projectKey}/model-governance`
- `GET /api/research/projects/{projectKey}/protocol/model-candidates`
- `GET /api/research/projects/{projectKey}/protocol/model-reviews`
- `GET /api/research/projects/{projectKey}/model-usage`
- `GET /api/research/model-evaluations`
- `GET /api/research/model-evaluations/{evaluationKey}`

全部使用 V2 `Envelope(data,meta)`、不透明 key 和字段白名单。普通响应不返回调用 UUID、任务 UUID、
内部章节 UUID、原始 Prompt、凭据引用、Base URL、对象 key 或模型原始响应。

### 4.2 动作

- `GENERATE_PROTOCOL_SECTION_CANDIDATE`
- `REVIEW_PROTOCOL_SECTION_CANDIDATE`
- `APPLY_PROTOCOL_SECTION_CANDIDATE`
- `REQUEST_DESIGN_MODEL_ADVICE`
- `START_ANONYMOUS_MODEL_EVALUATION`
- `SUBMIT_MEDICAL_EVALUATION_SCORE`
- `SUBMIT_STATISTICAL_EVALUATION_SCORE`

课题动作继续使用 `Idempotency-Key` 和 `If-Match`。评测启动仅医院管理员；专家评分只允许本院
EXPERT，且医学/统计评分人必须不同。候选采纳继续复用方案章节乐观版本。

## 7. Review 检查项

- 路由是否真的按逻辑类型返回不同配置，是否存在同模型自审或静默回退；
- 模型调用前是否完成外部开关、输入安全、价格、预算和路由身份检查；
- 审计是否准确记录实际路由、Prompt、Schema、Provider 用量和成本状态；
- Token 缺失或价格未知是否被误记为 0；
- 候选是否可能带入未分配 PMID、DOI、NCT、引用 key、内部 UUID 或 Prompt 指令；
- 候选生成是否会自动覆盖章节、绕过乐观锁、锁定状态或三方审核失效；
- 模型复核是否被错误计作人工医学/统计审核；
- 设计模型是否能绕过三类研究规则或掩盖缺失信息；
- 专家评分是否医院隔离、角色正确、两类专家不同账号且历史可追溯；
- 课题用量是否按本院/本课题 SQL 聚合，是否可枚举其他课题；
- 页面、导出和错误是否仍保持科研草案边界；
- 当前 V19 实例和外部供应商是否保持不变。
