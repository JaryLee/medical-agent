扫描使用只读事务，不执行删除、合并、修正、重编号或 DDL。应用当时仍在运行，因此首次目录扫描
不是维护窗口内的单一快照；测试后的精确行数复核使用
`REPEATABLE READ READ ONLY`。正式迁移前仍须停止旧 Worker 并重跑同一套扫描。

本报告检查：

- 真实 PostgreSQL 测试前后数据及 Flyway 临时库清理。

## 4. 医院隔离

动态检查了 80 组“子表和父表均有 `hospital_id`”的单列外键关系，当前跨医院不一致总数为 0。

该结果只证明现存行干净，不能证明未来写入安全。多数关系仍只有业务主键外键，没有
`(hospital_id, id)` 组合外键；P0-B 仍须补充：

- 组合唯一键与组合外键；
- 所有仓储查询的 `hospital_id` 条件；
- 两医院同标识、同用户名、同课题名的真实 PostgreSQL 负向测试。

## 5. Agent 迁移风险

当前快照：

- `WAITING_CONFIRMATION=1`，有一个正在等待人工确认的任务；
- `RUNNING` 且无租约：0；
- `RUNNING` 且租约过期：0；
- `QUEUED` 且残留租约：0；
- 步骤 `attempt_no <= 0`：0；
- 模型步骤记录 4 条，存在 4 个不同的随机 `model_call_id` 和 4 条 Prompt 记录；
- 开放确认步骤：1；
- 已检查的检索/验证/相似研究/设计任务重复组：0；
- 方向候选在 `directions` 或 `analysis.directions` 缺失：0。

仍存在结构性风险：

1. 当前 `model_call_id` 只是随机 UUID，没有模型调用日志外键，且记录发生在调用之后。
2. 当前 `task.version` 被复用为尝试次数，不能表达每步骤独立尝试。
3. 租约没有执行令牌、心跳和 fencing，旧 Worker 可能在租约丢失后覆盖新 Worker。
4. 方向候选没有候选集版本/哈希，确认后会重新生成，存在方向漂移。
5. 步骤、任务、事件和外部工具调用缺少统一事务/稳定操作键。

## 6. 迁移策略

### P0-A 上线顺序

当前存在一个等待确认任务且有 21 个会话。禁止旧 Worker 与新 Worker 混跑：

1. 开启维护窗口并阻止新任务创建；
2. 停止所有旧版本 Worker，确认无 `RUNNING` 任务；
3. 在单个只读、可重复读事务中重跑本报告扫描；
4. 备份数据库和对象存储清单；
5. 执行追加迁移，保留历史步骤和现有尝试号，不自动重编号；
6. 启动只包含新租约协议的 Worker；
7. 对等待确认任务做兼容读取和一次人工抽查；
8. 通过双 Worker、租约过期、崩溃重放和幂等测试后恢复流量。

迁移采用 forward-fix；不得回滚到会读取新表但不理解执行令牌的旧 Worker。

### 数据处置

本阶段没有发现需要自动清理的数据。即使后续扫描发现重复，也只生成候选报告；删除、合并、
重挂外键和覆盖用户输入必须由课题负责人逐项批准。
